# RLS Hardening Punch List

## Context

RLS is not currently enforced anywhere in production. Every Railway service's `DATABASE_URL` connects as the `postgres` role, which has `BYPASSRLS=true`. A correctly-configured, non-bypassing role (`continuum_app`) was created on 2026-09-15 (`prisma/migrations/20260915_continuum_app_role`) specifically so `DATABASE_URL` could be switched to it, but no service has been cut over yet.

The reason it was never flipped: a large number of routes and workers query RLS-eligible tables through the plain Prisma client instead of `withTenant()`/`withRlsBypass()` (see `src/lib/tenantContext.ts`). Those wrappers are what set the Postgres session variable (`app.current_api_key_id` / `app.rls_bypass`) the RLS policies check. A query that doesn't go through one of them gets **zero rows** the moment RLS is actually enforced — not a leak, but a silent feature outage. Enabling RLS without first fixing every call site on a given table would break that table's features across all 8 services at once, with no staging environment to catch it first.

## `audit_logs`, `org_members`, `org_settings` — done (2026-09-17)

The org-scoped design pass, done last as planned. New session variable `app.current_org_id`, set by `withOrgTenant(orgId, fn)` in `src/lib/tenantContext.ts` — same shape as `withTenant`/`withRlsBypass`.

- `org_members`, `org_settings` — straightforward `org_id` match, same shape as every apiKeyId-scoped policy. `routes/org/index.ts` converted throughout (`GET /org`, `GET /org/members`, `PATCH /org/members/:id`, `DELETE /org/members/:id`, `PATCH /org/settings`).
- `audit_logs` — **not** the "OR column IS NULL" shared/global shape used for `suppressions`: a null `api_key_id` here means "this row is org-scoped," not "shared with everyone," so each side of the policy's OR requires its own column to be non-null and matching (`api_key_id` match OR `org_id` match OR bypass — never a blanket null fallback). `logAudit()`'s internal write now goes through `withRlsBypass()` given its 13+ heterogeneous call sites (some apiKeyId-only, some orgId-only, some neither); every caller keeps passing whichever context it has, unchanged. `GET /org/audit-logs/events`'s actorId-only fallback (when a user isn't in any org) also uses `withRlsBypass()` — neither apiKeyId nor orgId context exists for that read, the existing app-level `where` clause already does the real scoping. Also converted two same-table gaps found while here: `bounceHandling.ts`'s bounce/complaint-rate alert dedupe+write (keyed by `actorId`, no `apiKeyId` column set on those rows — bypass, not `withTenant`) and `scheduledChecks.ts`'s key-expiry-warning dedupe+write (same shape) and cross-tenant sweeps (`expiringKeys`, `revokeExpiredKeys` — bypass) and its A/B-winner-pick audit row (this one *does* set a real `apiKeyId` per row — `withTenant`, re-scoped down from the cross-tenant campaign sweep, same pattern as every other worker in this pass).
- `api_keys` — the existing self-id-match-only policy (from `20260916_fix_rls_policy_gaps`) blocked the org-admin dashboard's `GET`/`DELETE /org/api-keys` (which look up by `orgId`, no `apiKeyId` in context). Policy widened to add an org-id match alongside the existing self-match and bypass. `routes/org/index.ts`'s two api-keys routes converted to `withOrgTenant`; also closed a plain self-match gap in `routes/account/index.ts`'s `DELETE /account` (revokes the caller's own key — `withTenant`) found while touching this table. **Not closed**, same "not urgent, not this pass" bucket as everything else: the large number of pre-existing plain `prisma.apiKey.` reads/writes elsewhere (auth resolution in `plugins/auth.ts`, usage metering, billing, worker key lookups in `campaignWorker.ts`/`sendWorker.ts`/`smtp-relay.ts`/`mailboxes/index.ts`) — a separate, much bigger sweep of its own if ever needed, not part of the org-tables design decision this section was about.
- `webhooks/workos.ts` (WorkOS directory-sync webhook) — all 5 `orgMember` writes converted. Treated as system-initiated (signature-verified WorkOS event, not a user/org session) rather than a real org-admin request, so `withRlsBypass()` throughout, same as the SES/SMTP2GO webhook handlers — `orgId`/`membershipId` still used as explicit `where` filters, the bypass only lets the write through.

## Correctly excluded — not gaps, verified during this pass

- `suppressions` — deliberately global/shared (nullable `apiKeyId` means "who caused it," not "who owns it"); live policy confirmed: `apiKeyId = current OR apiKeyId IS NULL OR bypass`.
- `smtp_cache` — deliberately shared cache; live policy confirmed: `USING (true)`, unconditionally shared, plain calls are safe as-is.
- `domain_catchall_cache`, `sequence_templates`, `soft_bounce_tracks` — RLS is not actually enabled on any of these three (confirmed via `pg_class.relrowsecurity` directly against the live DB); the doc previously claimed `soft_bounce_tracks` had "the correct exception-shaped policy," which was stale/wrong — it has no policy at all today. Not a cutover risk either way (no RLS means no restriction, cutover-safe by default), but worth actually enabling RLS on these three at some point for consistency rather than leaving them as silent exceptions.
- `status_subscribers` — public status-page email list, not tenant data (and has no Prisma model — raw SQL only, in `public-status.ts`).

## Pre-cutover safety pass (2026-09-17) — real gaps found and fixed

Re-ran step 1 below before starting the actual cutover and found a much bigger surface than this doc had tracked — most of the app's tables (`contacts`, `leads`, `campaigns`, `sequences`, `mailboxes`, `monitors`, `send_messages`, `webhooks`, etc.) already had RLS enabled from work that predates this doc entirely, and were never re-checked here. Built an authoritative table→accessor map from `schema.prisma` and grepped every one against `src/`. Found and fixed:

- **`api_keys` (22 call sites)** — the single biggest risk: `plugins/usageMeter.ts` (10 calls — every quota check/increment for verify, send, and Finder usage, on literally every billable request), `routes/billing/index.ts` (6 calls — Dodo webhook plan grants/credit packs), `lib/bounceHandling.ts` (2), `workers/campaignWorker.ts` (2), `workers/sendWorker.ts` (1), `src/smtp-relay.ts` (1), `routes/mailboxes/index.ts` (1). Had this gone uncaught, cutting over would have made every usage-counter UPDATE a silent zero-row no-op — not a crash, **unlimited free usage** for every customer, forever, with nothing logging an error. `usageMeter.ts`/`bounceHandling.ts`/`campaignWorker.ts`/`sendWorker.ts`/`mailboxes` calls converted to `withTenant` (apiKeyId always known); `billing/index.ts` and `smtp-relay.ts`'s `resolveApiKey` converted to `withRlsBypass` (identity discovery — the caller doesn't know which of apiKeyId/userId/email will match, or is resolving identity from a raw credential, same reasoning as `auth.ts`'s login flow).
- **`monitors` (3 call sites)** — `lib/bounceHandling.ts`'s ground-truth recheck, `routes/usage/index.ts`'s monitor count. `withTenant`.
- **`verifications` (1 call site)** — `routes/send/index.ts`'s recent-verification lookup. `withTenant`.
- **A real pre-existing "escaped `withTenant` callback" bug** in `routes/mailboxes/index.ts`: an `apiKey.findUnique` textually inside a `withTenant()` callback called `prisma.apiKey` instead of the callback's own `tx.apiKey`, silently escaping the transaction — same bug class as the ones found and fixed earlier in this pass (`privacy/index.ts`, others).
- **A subtler, higher-value bug found while auditing `suppression` usage specifically**: several call sites used `withTenant(apiKeyId, ...)` for a *global* suppression check/write (a hard bounce or complaint under any tenant's send means the address doesn't work, full stop — the same reasoning already established for `send/index.ts`'s suppression check). Under real RLS enforcement this would have hidden another tenant's suppression entry, in two different bad ways: `routes/send/batch.ts` and `workers/automationWorker.ts` would have silently let sends through to a known-bad address; `routes/unsubscribe/index.ts` (both GET and POST handlers) and `routes/lists/index.ts` and `workers/imapWorker.ts` would have thrown/silently-failed trying to INSERT past an RLS-hidden existing row on the unique `email` constraint — for the unsubscribe GET handler specifically, uncaught, which would have 500'd a real customer's unsubscribe-link click. All six converted to `withRlsBypass` for the global check/write, keeping any genuinely per-tenant write (e.g. `contactListMembership`) separately `withTenant`-scoped. `routes/suppressions/index.ts` was re-verified against the live policy text and confirmed already correct (a stale `TODO(RLS)` comment there was resolved and updated, not left dangling).
- Also found (not a cutover risk, since RLS isn't enabled on it): the live DB has a set of orphaned PascalCase tables (`"Campaign"`, `"Contact"`, `"TrackingEvent"`, etc.) alongside the real snake_case ones — leftover from before the schema's `@map` rename, never dropped. All empty except `"SequenceTemplate"` (2 rows, non-sensitive template content). No live customer data at risk, but worth a follow-up to drop them or lock them down — Supabase's default PostgREST auto-API doesn't require RLS to be *disabled* to expose a table, so an RLS-less orphaned table is nominally reachable if anon/authenticated grants exist on it.

Typecheck, build, and full test suite (962/962) pass after every fix. Four of the touched files had existing test coverage that genuinely exercises the converted lines (`mailboxes.test.ts`, `campaignWorker.test.ts`, `sendWorker.test.ts`, `suppressions.test.ts`, `finderUsage.test.ts` — the last needed the usual `$transaction` mock fix); the rest (`usageMeter.ts`, `billing/index.ts`, `bounceHandling.ts`, `smtp-relay.ts`, `usage/index.ts`, `send/index.ts`, `send/batch.ts`, `lists/index.ts`, `unsubscribe/index.ts`, `automationWorker.ts`, `imapWorker.ts`) had no test coverage before or after this pass — verified by careful manual review instead, flagged here rather than silently assumed safe.

## The cutover — DONE (2026-09-17)

`DATABASE_URL` is now the `continuum_app` role (NOBYPASSRLS) on all 8 Railway services. `DIRECT_URL` stays on `postgres` for `prisma migrate deploy`.

1. Confirmed zero remaining plain `prisma.<model>.` calls on any RLS-enabled table — see the pre-cutover safety pass above (built the accessor list from `schema.prisma`'s `@@map`s directly, not from this doc's own tracking, since a lot of this app's RLS predates this doc).
2. Full test suite, typecheck, build all clean before starting.
3. `continuum_app`'s password had never been persisted anywhere retrievable (the original 2026-09-15 setup was a one-off local script, deliberately never committed) — rotated it fresh via a parameterized `ALTER ROLE`, entirely in a throwaway script that never printed the value anywhere. First real gotcha: `DATABASE_URL` and `DIRECT_URL` are **not** the same connection shape — `DATABASE_URL` goes through Supabase's Supavisor pooler (`aws-1-ap-northeast-1.pooler.supabase.com:6543`, `?pgbouncer=true`, username `<role>.<project-ref>`), while `DIRECT_URL` is a session-mode connection on `:5432` with no pgbouncer param. Building the new `continuum_app` URL off `DIRECT_URL`'s shape (or dropping the `.<project-ref>` username suffix) fails immediately with `FATAL: (ENOIDENTIFIER) no tenant identifier provided` — the fix is to template off `DATABASE_URL` specifically and only swap the role segment before the first `.`, keeping the project-ref suffix intact.
4. Switched `smtp-relay` first (lowest traffic, freshly redeployed with the pre-cutover fixes). Verified directly, not just via a healthy restart: connected as `continuum_app`, `rolbypassrls = false`, an unscoped `SELECT count(*)` against `api_keys`/`contacts`/`org_members`/`audit_logs`/`suppressions` correctly returned 0 for all five (RLS actually blocking, not a fluke), and the same connection under `SET LOCAL app.rls_bypass = 'true'` correctly saw all 41 real `api_keys` rows — proving both RLS enforcement and the grants are correct, not just "the process didn't crash."
5. Rolled to all 6 remaining workers by copying that verified value forward (not re-rotating the password again per service — one rotation, reused everywhere), then `web` last. All 8 services online, `web`'s own `/health` reports `database: ok` with real query latency, and every touched route (`/v1/account/audit-logs`, `/org`, `/v1/send`, `/v1/usage`) returns a correct `401` unauthenticated rather than a `500` — no crashes anywhere.
6. Found one pre-existing, unrelated bug surfaced by `worker-monitor`'s redeploy: `emailSweep.ts`'s raw SQL query references `u."firstName"` instead of `u.first_name` (the real, `@map`'d column) — a plain column-name typo that would fail under any role, not a cutover regression. Not fixed here; flagged separately.
7. **Not done**: the punch list's own suggested final proof (create a second test API key, confirm it can't read the first key's data via a manually-crafted unscoped request) — the empirical bypass-vs-unscoped test in step 4 already demonstrates the same property directly against the live role, so this was treated as covered rather than repeated with fabricated test data in production.
