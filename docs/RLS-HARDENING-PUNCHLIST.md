# RLS Hardening Punch List

## Context

RLS is not currently enforced anywhere in production. Every Railway service's `DATABASE_URL` connects as the `postgres` role, which has `BYPASSRLS=true`. A correctly-configured, non-bypassing role (`continuum_app`) was created on 2026-09-15 (`prisma/migrations/20260915_continuum_app_role`) specifically so `DATABASE_URL` could be switched to it, but no service has been cut over yet.

The reason it was never flipped: a large number of routes and workers query RLS-eligible tables through the plain Prisma client instead of `withTenant()`/`withRlsBypass()` (see `src/lib/tenantContext.ts`). Those wrappers are what set the Postgres session variable (`app.current_api_key_id` / `app.rls_bypass`) the RLS policies check. A query that doesn't go through one of them gets **zero rows** the moment RLS is actually enforced — not a leak, but a silent feature outage. Enabling RLS without first fixing every call site on a given table would break that table's features across all 8 services at once, with no staging environment to catch it first.

## `audit_logs`, `org_members`, `org_settings` — done (2026-09-17)

The org-scoped design pass, done last as planned. New session variable `app.current_org_id`, set by `withOrgTenant(orgId, fn)` in `src/lib/tenantContext.ts` — same shape as `withTenant`/`withRlsBypass`.

- `org_members`, `org_settings` — straightforward `org_id` match, same shape as every apiKeyId-scoped policy. `routes/org/index.ts` converted throughout (`GET /org`, `GET /org/members`, `PATCH /org/members/:id`, `DELETE /org/members/:id`, `PATCH /org/settings`).
- `audit_logs` — **not** the "OR column IS NULL" shared/global shape used for `suppressions`: a null `api_key_id` here means "this row is org-scoped," not "shared with everyone," so each side of the policy's OR requires its own column to be non-null and matching (`api_key_id` match OR `org_id` match OR bypass — never a blanket null fallback). `logAudit()`'s internal write now goes through `withRlsBypass()` given its 13+ heterogeneous call sites (some apiKeyId-only, some orgId-only, some neither); every caller keeps passing whichever context it has, unchanged. `GET /org/audit-logs/events`'s actorId-only fallback (when a user isn't in any org) also uses `withRlsBypass()` — neither apiKeyId nor orgId context exists for that read, the existing app-level `where` clause already does the real scoping. Also converted two same-table gaps found while here: `bounceHandling.ts`'s bounce/complaint-rate alert dedupe+write (keyed by `actorId`, no `apiKeyId` column set on those rows — bypass, not `withTenant`) and `scheduledChecks.ts`'s key-expiry-warning dedupe+write (same shape) and cross-tenant sweeps (`expiringKeys`, `revokeExpiredKeys` — bypass) and its A/B-winner-pick audit row (this one *does* set a real `apiKeyId` per row — `withTenant`, re-scoped down from the cross-tenant campaign sweep, same pattern as every other worker in this pass).
- `api_keys` — the existing self-id-match-only policy (from `20260916_fix_rls_policy_gaps`) blocked the org-admin dashboard's `GET`/`DELETE /org/api-keys` (which look up by `orgId`, no `apiKeyId` in context). Policy widened to add an org-id match alongside the existing self-match and bypass. `routes/org/index.ts`'s two api-keys routes converted to `withOrgTenant`; also closed a plain self-match gap in `routes/account/index.ts`'s `DELETE /account` (revokes the caller's own key — `withTenant`) found while touching this table. **Not closed**, same "not urgent, not this pass" bucket as everything else: the large number of pre-existing plain `prisma.apiKey.` reads/writes elsewhere (auth resolution in `plugins/auth.ts`, usage metering, billing, worker key lookups in `campaignWorker.ts`/`sendWorker.ts`/`smtp-relay.ts`/`mailboxes/index.ts`) — a separate, much bigger sweep of its own if ever needed, not part of the org-tables design decision this section was about.
- `webhooks/workos.ts` (WorkOS directory-sync webhook) — all 5 `orgMember` writes converted. Treated as system-initiated (signature-verified WorkOS event, not a user/org session) rather than a real org-admin request, so `withRlsBypass()` throughout, same as the SES/SMTP2GO webhook handlers — `orgId`/`membershipId` still used as explicit `where` filters, the bypass only lets the write through.
- `auth/index.ts`'s login-callback `orgMember.upsert` — `workosOrgId` is known and trusted at that point (already used directly in the write), unlike the identity-discovery apiKey/teamMember/teamInvite calls around it — `withOrgTenant`, not `withRlsBypass`.

Migration: `20260917_rls_org_scoped_tables`. Verified live via direct SQL: all 4 policies present with the expected `qual`, `relrowsecurity = true` on all 4 tables. Typecheck, build, and full test suite (945/945) pass — two test files needed the usual `prisma.$transaction = vi.fn((fn) => fn(prisma))` mock fix (`audit.test.ts`, `org-api-keys.test.ts`).

## The cutover itself (do this last, after everything above is done and tested)

1. Confirm zero remaining plain `prisma.<model>.` calls on any RLS-enabled table:
   ```
   grep -rn "prisma\.\(<every RLS model name>\)\." src --include="*.ts" | grep -v __tests__
   ```
2. Run the full test suite and a full manual smoke pass across every major flow (verify, bulk, campaigns, sequences, team, billing, connectors, Salesforce, agent runs) — there's no staging environment, so this has to be thorough.
3. Switch `DATABASE_URL` to the `continuum_app` role on **one low-traffic worker first** (e.g. `worker-webhook` or `smtp-relay`), not `web`. Watch logs closely for a few minutes.
4. Roll to the remaining workers one at a time, `web` last (highest blast radius, most call sites).
5. Once fully cut over, verify the actual security property empirically: create a second test API key, confirm it cannot read the first key's contacts/leads/suppressions/etc. even with a manually-crafted request that omits a `WHERE apiKeyId` filter (this is the real proof RLS is doing something — everything before this step is prep).
